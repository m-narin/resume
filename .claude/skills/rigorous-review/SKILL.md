# Rigorous Review（徹底レビュー & 自動修正）

変更差分に潜む **不備（バグ・異常系・並行性・セキュリティ）** と **漏れ（仕様・要件に対する実装漏れ・考慮漏れ）** を、エージェントチームで徹底的に洗い出し、確信の高いものは自動修正する。

設計の芯は **「広く検出 → 敵対的に検証 → 高確信だけ直す」**。検出は再現率（取りこぼさない）を優先して多レンズでファンアウトし、そのままだと混じる誤検知を、独立した懐疑エージェントの**多数決反証**で削る。確証が取れたものだけを直すので、自動修正でも壊しにくい。

## このスキルの位置づけ（既存レビューとの違い）

- `my-review` がコード品質・規約・PRコメント投稿（修正しない）なのに対し、本スキルは **不具合と仕様漏れに集中** し、**高確信は自動修正**する
- レビュー観点の網羅は Workflow の **loop-until-dry**（出尽くすまで巡回）+ **敵対的多数決検証** で担保する
- 静的な読解だけでなく、プロジェクトの **typecheck / lint / test を実際に走らせて一次証拠**にする

## 前提

- git リポジトリ内で作業していること
- PR を対象にする場合は `gh` CLI が認証済みであること
- このスキルは **Workflow ツール** を使う（多数エージェントを起動するため相応のトークンを消費する。「徹底」志向なので想定どおり）

## ステップ 1: スコープ判定

何をレビュー対象にするかを次の優先順で自動判別する。判定結果（対象・`diffCmd`・変更ファイル）はこの後ずっと使うので明確に確定させる。

1. **引数に PR 番号 / URL がある** → **PR スコープ**
   - 現在のブランチ名を記憶（最後に戻すため）。`gh pr checkout <n>` でチェックアウト
   - `diffCmd = "gh pr diff <n>"`、変更ファイル = `gh pr view <n> --json files --jq '.files[].path'`
2. **引数なし** → `git status --porcelain` を見る
   - **未コミット変更あり** → **作業ツリースコープ**（コミット前の最終確認）
     - `diffCmd = "git diff HEAD"`（staged + unstaged の両方）、変更ファイル = `git diff HEAD --name-only`
   - **未コミット変更なし** → **現ブランチ vs デフォルトブランチ スコープ**
     - まず **デフォルトブランチ名を判定**する（後述 1-A）。`main` 固定にしない（リポジトリにより `master` / `develop` / `development` などのことがある）
     - `base = $(git merge-base HEAD <デフォルトブランチ>)`（ローカルに無ければ `origin/<デフォルトブランチ>` を使う）
     - `diffCmd = "git diff <base>...HEAD"`、変更ファイル = `git diff <base>...HEAD --name-only`
     - 現ブランチ自体がデフォルトブランチの場合は比較対象が無いので、差分 0 件として扱い終了する

変更ファイルが 0 件なら「レビュー対象の差分がありません」と報告して終了する。

### 1-A. デフォルトブランチの判定

`main` を決め打ちせず、次の優先順で解決する（このスキルは複数リポジトリで使う前提のため、リポジトリごとに自動判別する）:

1. **ユーザーが比較対象ブランチを明示**していれば、それを使う（最優先。例:「develop と比べて」）
2. リモートの既定ブランチ: `git symbolic-ref --quiet --short refs/remotes/origin/HEAD`（→ `origin/main` 等）から先頭の `origin/` を除いた名前。ネットワーク不要で最も確実
3. 上が空なら（`origin/HEAD` 未設定）: `git remote show origin` の `HEAD branch:` 行（リモート問い合わせが要る場合あり）
4. リモートが無い／取れない場合: ローカルに存在する一般的な既定名を **`main` → `master` → `develop` → `development` → `trunk`** の順で探し、最初に見つかったものを使う
5. それでも決まらなければ、ユーザーに「どのブランチと比較するか」を尋ねる（黙って `main` にフォールバックしない）

## ステップ 2: コンテキスト収集（仕様 & チェックコマンド）

検出・検証エージェントに渡す **仕様コンテキスト** と、裏取り用の **チェック結果** を用意する。

### 2-A. 仕様・要件コンテキスト（`specContext`）

「漏れ」を見るには、実装が満たすべき要件が要る。スコープに応じて集める:

- **PR スコープ**: `gh pr view <n>`（本文を**精読**）+ リンクされた Issue 本文。`my-review` 同様、本文で「容認・温存・スコープ外」と明示された事項があれば抜き出し、「これらは意図的な判断なので指摘から除外する」と添える
- **作業ツリー / ブランチ スコープ**: ブランチ名 + 当該ブランチのコミットメッセージ群（`git log <base>..HEAD --format='%s%n%b'`）。現ブランチに紐づく PR があれば `gh pr view` も使う
- **どこにも要件が見つからない場合**: `specContext` に「仕様情報なし。意図はコードとコミットから推測。要件不明な箇所は推測である旨を明記して報告」と書く（充足性班に推測前提を伝えるため）

`specContext` は要約テキスト 1 つにまとめる。長い PR 本文は要点（やること・仕様判断・考慮事項）に圧縮してよい。

### 2-B. チェックコマンドの検出と実行（`checkResults`）

プロジェクトのチェック手段を検出し、**静的で高速なものは必ず実行**して失敗を捕まえる。失敗は最強の一次証拠になる。

検出のヒント（プロジェクトに合わせて選ぶ）:

| 種別 | 例 |
|---|---|
| TypeScript/JS | `package.json` の `typecheck` / `lint` / `test` / `build` スクリプト（pnpm/npm/yarn）、`tsc --noEmit` |
| Make | `Makefile` の `test` / `lint` / `typecheck` / `check` ターゲット |
| Go | `go build ./...` / `go vet ./...` / `go test ./...` |
| Rust | `cargo check` / `cargo clippy` / `cargo test` |
| Ruby | `bundle exec rubocop` / `rspec` |
| Python | `ruff` / `mypy` / `pytest` |

方針:

- **typecheck と lint は必ず実行**（速くて信号が強い）
- **test / build は存在すれば実行**。ただし重い統合テスト（DB/Docker 起動が要る等）やタイムアウトしそうなものは無理に走らせず、**走らせなかったものは明示**する（黙って省略しない）
- 失敗があれば、該当箇所・エラー行を `checkResults` に要約して入れる。全て通れば「typecheck/lint/test: 全て通過」、未実行があれば「build: 未実行（重いため手動推奨）」のように書く
- このとき走らせたコマンド群は**記憶**しておく（ステップ 5 の回帰確認で同じものを再実行する）

## ステップ 3: Workflow で検出 → 敵対的検証

バンドルした Workflow スクリプトを起動する。検出と検証のファンアウトはすべてこのスクリプトが決定的に制御する。

このスキルディレクトリの `scripts/review-workflow.js` の**絶対パス**を `scriptPath` に渡し、ステップ 1〜2 で集めた情報を `args` に渡す:

```
Workflow({
  scriptPath: "<このスキルの絶対パス>/scripts/review-workflow.js",
  args: {
    scopeLabel: "PR #123 (owner/repo)",         // 人間向けの対象説明
    diffCmd: "gh pr diff 123",                  // 差分を表示するコマンド（ステップ1で確定したもの）
    changedFiles: ["src/foo.ts", "src/bar.ts"],
    specContext: "<ステップ2-Aで作った要約>",
    checkResults: "<ステップ2-Bの結果サマリ>",
    thoroughness: "thorough"                    // 通常は "thorough"。差分が小さい/急ぐときだけ "standard"
  }
})
```

- `thoroughness`: 既定は `"thorough"`（全6レンズ × 最大2巡）。変更が数十行以下で軽く見たいときや、コストを抑えたいときは `"standard"`（主要3レンズ × 1巡）にする
- **コスト注意**: このスキルは多数のサブエージェントを起動するため、`thorough` は **差分規模に応じて数百万トークン**かかりうる。数百行を超える大きな PR では `"standard"` を選ぶか、対象を絞る（特定ディレクトリの diff にする等）ことを検討し、その旨をユーザーに一言伝える
- 各巡は「全レンズ検出 → 意味的 dedup（同根の重複を1件に統合）→ 各指摘を敵対的検証」の順。dedup を挟むことで、同じ欠陥が複数レンズから重複報告されても確定は1件にまとまる
- 戻り値は `{ scopeLabel, stats, confirmed }`。`confirmed` が**敵対的検証を生き残った確定指摘**の配列。各要素は `{ title, file, line, severity, category, description, evidence, fixConfidence, suggestedFix, verification }`。`stats.totalDetected`（生検出数）と `confirmedCount` の差が、dedup と検証で削られた量の目安
- `confirmed` が空なら、ステップ 6 で「確定した不備・漏れはありませんでした」と報告して終了（検出はされたが検証で全て棄却された場合は、その旨も添える）

> 補足: Workflow ツールが使えない環境では、`scripts/review-workflow.js` の検出レンズ・検証ルール・多数決ロジックを手本に、Agent ツールで検出エージェントを並列起動 → 各指摘を懐疑エージェントで反証（critical/high は 3、medium/low は 1）→ 過半数反証なら棄却、という流れを手動で再現する。

## ステップ 4: 自動修正（直列）と「要判断」の振り分け

`confirmed` を **修正の確信度（fixConfidence）と積極度（aggressiveness）** で振り分ける。並列で同じファイルを編集すると壊れるので、**修正は main 側で直列に**適用する（Workflow は検出・検証のみ）。

**積極度** はユーザーの指示から決める（明示が無ければ `balanced`）。境界をどこに置くかだけが変わる:

| 積極度 | 自動修正する範囲 | 合図の例 |
|---|---|---|
| `conservative` | `fixConfidence == high` かつ severity が critical/high のものだけ | 「慎重に」「最小限だけ」 |
| `balanced`（既定） | `fixConfidence == high`（全 severity） | 既定 |
| `aggressive` | `fixConfidence == high` + `medium` | 「できるだけ直して」「全部直して」 |

- 自動修正対象に当てはまらないものは **「要判断」として報告のみ**（設計判断・仕様解釈・大きめのリファクタを伴うものは勝手に直さない）
- `aggressive` で medium まで直すのが許容できるのは、**ステップ 5 の修正再検証が安全網**として効くため（回帰の疑いがあれば巻き戻す）

自動修正の進め方:

1. 対象を**ファイル単位でまとめ**、ファイルごとに `Read` → `Edit` で適用する（同一ファイルへの複数修正をまとめて当てて衝突を避ける）
2. 各修正は `suggestedFix` を出発点に、周辺コードの規約・既存パターンに合わせて**最小限**で当てる。提案が不適切なら、指摘の趣旨に沿ってより良い修正にしてよい
3. プロジェクトの規約（命名・ログ・エラーハンドリング等）に従う。リポジトリに CLAUDE.md 等の規約があれば尊重する
4. **適用した各修正を控えておく**（指摘・対象ファイル・実際に当てた変更）。ステップ 5 の再検証に渡す
5. **コミットはしない**（diff はユーザーが確認してから自分でコミットする）

## ステップ 5: 修正の再検証（適用した修正を敵対的に点検）

自動修正は「指摘を解消したつもり」で別の問題を生むことがある（戻り値の形を変えて呼び出し元を壊す、表面的に直して根本が残る等）。検出・検証と同じ敵対的姿勢を**修正そのものにも適用**する。これがあるので `aggressive` でも壊しにくい。

自動修正を 1 件以上適用した場合、バンドルの `scripts/verify-fixes-workflow.js` を起動する:

```
Workflow({
  scriptPath: "<このスキルの絶対パス>/scripts/verify-fixes-workflow.js",
  args: {
    scopeLabel: "<ステップ1と同じ対象説明>",
    diffCmd: "<修正適用後の差分コマンド。作業ツリーなら git -C <dir> diff HEAD>",
    fixes: [
      // ステップ4で控えた、自動修正したものだけ
      { title, file, line, severity, category, findingDescription, suggestedFix, appliedChange }
    ]
  }
})
```

戻り値 `verdicts[].verdict.decision` に従って後処理する:

- `keep`: そのまま維持
- `revert`: **その修正を巻き戻す**（`git checkout -- <file>` や逆 Edit で元に戻す）。回帰の疑いがあるため自動修正をやめ、「要判断」に降格してテーブルに残す
- `manual`: 適用は残すが「🔁 要確認」と明示する（解消が不完全な可能性。人間の確認を促す）

自動修正が 0 件なら省略する。

## ステップ 6: チェック再実行（回帰確認）

修正（とステップ 5 の巻き戻し）を反映したら、ステップ 2-B で**実際に走らせたコマンドを同じ条件で再実行**し、新たな失敗を生んでいないか確認する。

- **修正で新たな失敗が出た** → 直し直す。直せなければその修正だけ巻き戻し、テーブルで「自動修正を見送り（チェックが落ちたため要判断に降格）」と明記する
- **修正前から落ちていた無関係な失敗が残る** → スコープ外として「既存の失敗（本修正と無関係）」と注記する
- 自動修正が 0 件だった場合、この再実行は省略してよい

## ステップ 7: 重要度順テーブルで報告

結果を会話に提示する（ファイルや外部サービスには書き込まない）。

まず**対応サマリ**（自動修正 N 件 / 要判断 M 件 / 巻き戻し K 件 / チェック状況）を一文で述べ、続けてテーブル:

```
| # | 重要度 | 種別 | 箇所 | 指摘 | 対応 | 根拠・検証 |
|---|--------|------|------|------|------|------------|
| 1 | Critical | security | backend/src/auth.ts:42 | 認可チェック漏れ | ✅ 修正済み | 反証 0/3・再検証 keep |
| 2 | High | correctness | frontend/app/x.tsx:88 | 空配列で undefined 参照 | 🔁 修正済み・要確認 | 再検証 manual（解消が不完全の疑い） |
| 3 | High | error-handling | backend/src/z.ts:20 | 例外の握り潰し | ↩️ 巻き戻し→要判断 | 再検証 revert（呼び出し元への回帰疑い） |
| 4 | High | spec-gap | backend/src/y.ts:15 | 要件の「下書き状態」が未実装 | ⚠️ 要判断 | 設計判断を伴う |
```

- **重要度**: critical / high / medium / low（`confirmed` の値をそのまま使う）
- **対応**: `✅ 修正済み`（再検証 keep）/ `🔁 修正済み・要確認`（再検証 manual）/ `↩️ 巻き戻し→要判断`（再検証 revert またはチェック失敗で降格）/ `⚠️ 要判断（未修正）`
- テーブルの下に、各指摘の**詳細**（何が・なぜ問題か、修正したものは修正内容、要判断・要確認のものは推奨対応の選択肢）を添える
- **敵対的検証で棄却した候補**があれば、透明性のため末尾に短くサマリ（「◯◯は『既にガード済み』と反証され棄却」等）。`stats` の `totalDetected` と `confirmedCount` の差が棄却数の目安
- 最後に **チェックの最終状況**（typecheck/lint/test の通過可否、未実行のもの）と「**コミットはしていない**ので diff を確認してからコミットしてください」を明記する

## 設計メモ（なぜこの形か）

- **検出と検証を分離**するのは、1 つのエージェントに「広く挙げて」と「厳しく絞って」を同時にやらせると、再現率か適合率のどちらかが崩れるため。検出は再現率特化で多レンズ・loop-until-dry、検証は適合率特化で敵対的多数決、と役割を割り切っている
- **検証エージェントの既定スタンスを「反証」**にしているのは、自動修正の前段だから。確証が取れないものを通すより、取りこぼしてもいいから誤検知を確実に落とす方が、勝手な修正で壊すリスクを下げられる
- **fixConfidence で自動/要判断を分ける**のは、「直して」依頼でも設計判断まで機械が断定すると事故るため。境界は「機械的に確実か」に置き、迷うものは人間に返す。積極度ノブはこの境界を可変にするだけで、判断の安全性は次の再検証で担保する
- **修正そのものを再検証する**（ステップ5）のは、自動修正が別の問題を生む（呼び出し元の破壊・表面的修正）リスクがあるから。検出→検証で使う敵対的姿勢を修正後にも適用し、回帰の疑いがあれば巻き戻す。チェック再実行だけでは、テストが無い箇所の修正の正しさを保証できない
- **検証の投票数を重要度で変える**（critical/high=3、medium/low=1）のは、検証がコストの主因だから。誤判定の影響が大きい高重要度には厚く、低重要度には薄く配分してコストと精度を両立する
- **チェックを実際に走らせる**のは、静的読解だけだと型エラーやテスト失敗という確実な不備を見逃すから。再実行で回帰も拾える
